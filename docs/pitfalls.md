## 一、模型网关与配额

### 百炼 `Model.AccessDenied`

- **现象**：对话/生图调用百炼返回 `Model.AccessDenied`，配置看起来都对。
- **根因**：API Key、`BAILIAN_WORKSPACE_ID` 与模型授权不属于**同一个业务空间**。百炼的 Key 是业务空间级的，跨空间即使 Key 有效也无权访问该空间的模型。
- **修法**：确保三者同属一个业务空间；用目标空间的 Key 重新签发；华北 2（北京）用同空间的 Workspace ID + Region。
- **预防**：上线 checklist 里固定一条「Key 属于目标业务空间且该空间已授权对话模型」；配置详见 [overview.md](./overview.md)。

### 上游网关静默换模型 / 回退，导致产物不可信

- **现象**：桌宠生图/质检偶发使用了非预期模型，落库的模型溯源对不上。
- **根因**：早期实现按模型名**前缀匹配**判定路由，`gpt-image-2-qwen-fallback` 这类别名会骗过前缀匹配；且失败时会静默回退到默认 Bailian/Qwen 客户端。
- **修法**：`apps/api/src/workflow/codex-pet/codex-pet-model-contract.ts` 改为**显式允许名单**（`CODEX_PET_IMAGE_MODEL_ALLOWLIST`）；质检模型按名字解析到 `chatgpt_model_route` / `bailian_model_route`，非法模型抛**不可重试**的 `CodexPetModelContractError`；Worker 健康就绪前校验路由存在且凭据有效，**禁止回退**。
- **预防**：涉及付费/交付的模型选择一律写成硬合同 + 允许名单，拒绝前缀匹配；新业务线复用这一模式。详见 [codex-pet.md](./codex-pet.md)。

### 第三方中继的 60s 读超时：长耗时调用必须流式保活

- **现象**：经第三方中继调 gpt-image-2 出图，约 50% 概率失败，错误只有一句 `fetch failed`，看起来像尺寸或画质问题。
- **根因**：中继是 nginx，`proxy_read_timeout` 默认 **60s**；非流式出图要等整图就绪才回第一个字节，而真实耗时 56–555s。成败纯粹取决于「有没有跑进 60s」。直连探针拿到硬证据：`SocketError: other side closed` 精确发生在 60.6s——**服务端主动断连**，本地把超时加到 600s 也没用。
- **修法**：改流式（`stream=true` + `partial_images`），响应头 15s 就到，之后 partial 事件持续喂数据，读超时永不触发。注意这只解决第一道超时——修完可能暴露第二道（错误从 `other side closed` 变成 `terminated`），undici 默认 `bodyTimeout` 300s 计的是 **chunk 间隔**而非总时长，是常见嫌疑。详见 [image.md](./image.md) 6.8、6.9。
- **预防**：接任何长耗时上游（出图/出视频/长文本）先问「中继有没有读超时」，默认假设有 60s 级限制，优先流式。诊断 `fetch failed` 一定要用直连探针打完整 `error.cause` 链——这句话本身不含任何信息。修掉一道超时后假设还有下一道，逐层验证到真实成功为止。

### 对话模型列表混入音频 / Realtime / 图片模型

- **现象**：AI Pixel 上游模型列表很杂，直接透出会让对话选项出现无法对话的模型。
- **根因**：把上游全量列表当作对话可选项。
- **修法**：用 `CHATGPT_MODELS` 白名单只放开会对话的 GPT 系列（`gpt-5.4`/`gpt-5.5`/`gpt-5.6-*` 等），旧 GPT、音频、Realtime、图片模型一律不进对话选项。
- **预防**：任何"可选模型"都以显式白名单为准，不信任上游列表。

## 二、向量与数据库迁移

### embedding 维度从 4096 迁到 1024

- **现象**：更换 embedding 模型为 `text-embedding-v4` 后，历史派生向量维度（4096）与新维度（1024）不一致，检索报错/失真。
- **根因**：向量维度是索引结构的一部分，不能与新模型混用。
- **修法**：迁移**清除旧派生向量、保留原始文档**，对三张向量表（`Memory`/`Chunk`/`NovelVectorMemory`）重建 HNSW 余弦索引，并把原始知识库文档重新排队索引。
- **预防**：牢记「派生数据可重算，原始数据不可丢」；换 embedding 模型必然伴随重建索引的迁移。详见 [overview.md](./overview.md)。

### Prisma 迁移记录漂移（本地）

- **现象**：本地库结构曾手工同步过，`prisma migrate deploy` 提示迁移记录与实际结构不一致，`pnpm dev` 启动受阻。
- **根因**：手工改库使 `_prisma_migrations` 记录与真实 schema 漂移。
- **修法**：`scripts/dev-local.sh` 对启动迁移失败**只警告不中断**；需要时 `DEV_SKIP_MIGRATIONS=1 pnpm dev` 跳过启动迁移。
- **预防**：本地尽量走迁移而非手改库；逃生阀仅限本地，生产发版迁移是硬门禁（见下）。

### 生产 RDS 缺 pgvector 扩展白名单

- **现象**：迁移执行 `CREATE EXTENSION vector` 被拒。
- **根因**：云 RDS 默认未启用 pgvector 扩展白名单；旧 PG12 也不带新版 pgvector。
- **修法**：控制台启用扩展白名单，使用 PG15/16，迁移账号需有建扩展权限。
- **预防**：上线 checklist 固定「RDS 已启用 pgvector 白名单；migrate Job complete」。详见 [overview.md](./overview.md)。

## 三、异步任务与计费一致性

### 退款漏掉 / 重复结算 / 并发状态错乱

- **现象**：本地商家宣传（promo）业务线曾出现退款与并发状态同步问题（yun-claude 07-08 多次修复）。
- **根因**：轮询、上游回调、reaper 三个入口各自处理终态，容易重复结算或漏退款。
- **修法**：把 finalize 收敛成**一个幂等函数**，三个入口共用（如 `workflow/dub-finalize.ts` + `dub-reaper.ts`）；以 `operationId` 作幂等键。
- **预防**：所有付费异步任务遵循统一的「reserve → 执行 → settle/refund」计费包裹范式，finalize 必须幂等。详见 [billing.md](./billing.md)。

### 按「请求参数」计费，上游却缩水交付

- **现象**：形象照请求 2K（`1728×2304`）按 2K 收费，实际交付的图只有约 1.573 MP——和 1K 请求出的图**像素完全相同**，钱收了双倍。库里查不出来。
- **根因**：中转上游对 gpt-image-2 只认宽高比、忽略绝对像素；而 `ImageAsset` 只有一列 `size` 记「请求尺寸」，从没记过「交付尺寸」，多收在数据层**没有痕迹**。
- **修法**：`ImageAsset` 加可空 `width`/`height`（迁移 `20260727160000_image_asset_delivered_size`），在 `storeWorkflowImage` 用 sharp 量一次真实宽高（一个测量点覆盖全部写库点）；计费改成 `reserveResource(请求档)` → 出图 → `settleResource(交付档)`，Go 侧 `settlePricedUsage` 自动退差额，无需新增原语。定档只降不升，一批图取最小那张，历史 `null` 行回退请求档。详见 [image.md](./image.md) 6.11。
- **预防**：**请求值和交付值分两列落库**，计费一律用交付值；经中转的调用尤其如此（同源问题见本文件「上游网关静默换模型」与 image.md 6.6）。取整方向永远选对用户有利的一边。

### 契约改造漏掉集成测试的 mock

- **现象**：桌宠启动路由从 `chargeResource` 改成 `reserveResource` 后，`codex-pet-routes.integration.test.ts` 一直红着（`expected 503 to be 202`），被当成「环境问题」放了很久。
- **根因**：测试的 billing mock 只有 `chargeResource`，新路由 `if (!billing.reserveResource) throw` 直接走进 503 分支。断言也还写着旧口径（`billingChargeStatus: "charged"`）。同一次改造还顺手弄丢了 `run.queued` 事件——它原来由 reconciler 在扣费确认后写，新路由创建时已是 queued 状态，没人补写，前端时间线的第一条就空了。
- **修法**：mock 补 `reserveResource`/`settleResource`，断言改成 `reserved` + `billingReservedUnits: 14`；在启动事务里补回 `run.queued` 事件（`lastEventSequence: 1`）。
- **预防**：把「一直失败的测试」当成待查缺陷而不是环境噪音——先看响应体再归因（这次 `503` 的 body 直接写着「调用额度预留失败」）。改计费契约时，能力检查（`if (!billing.x) throw`）会把 mock 缺口伪装成运行时故障；同时清点旧路径**副作用**（事件、通知、状态字段）有没有跟着搬家。

### 不可逆的结清挂在「失败」事件上，把可重试失败变成永久死刑

- **现象**：桌宠 `老鼠猫` 运行因一个纯代码 bug 失败。bug 修好、9 组动作按已付费素材零成本重导、图集本地验证 0 错 0 警之后，把运行解冻回执行态，worker **确实来领了活，然后立刻返回 `billing_pending` 走掉**，怎么都跑不起来。用户视角就是「钱真扣了，图一直不给」。
- **根因**：失败处理路径顺手调了 `settleResource`（`billingSettledAt` 与失败时刻同一毫秒）。而所有恢复路径都硬性要求 `billingSettlementStatus === "reserved"`（worker 领活资格、额外调用授权），于是**结清即终态**：工作流状态怎么改都救不回来。失败本是**可修复的中间态**（素材完好），结清是**终态动作**，把终态动作绑在可修复事件上，等于让每一次中途失败都对整个运行判死刑。
- **修法（已修）**：分两步。① 交付兜底：用一次性脚本从已付费的存量帧纯确定性拼装出交付物并入库（零生图调用、零计费写入），产物 `expiresAt` 置 `null` 而非中间产物 TTL——否则 7 天后删掉就又回到「扣了费不给图」。运行状态改回终态，因为执行态会占用「已有活跃运行」名额、把用户锁在新建之外。② 根因：把结清从失败路径上摘下来，改成**有界的可续跑窗口**——失败不再结清，由已有的定时清算在宽限期（默认 24h，`CODEX_PET_FAILED_SETTLEMENT_GRACE_MS`）后兜底关账。
- **为什么不是「只在真终态结清」**：预留会**占住**用户余额。永不结清失败运行，等于把「无界的判死刑」换成「无界的冻结」——每个没人回头看的失败运行都永久占着额度。窗口把两头都收住。而且**延后结清更准**：结清单位是结清那一刻从调用流水重新点的，续跑后按真实最终次数结。
- **落地时的两个坑**：① 清算任务通常**已经**在扫终态运行（本例每 60s 一轮），所以只删掉失败路径里的内联结清只买到 60 秒——宽限期必须做进清算任务本身，否则等于没做。② 一个未花钱的失败（零次已发调用）应当**立即**结清释放预留：无可续跑之物，白冻用户额度没有意义。
- **窗口必须配一条真能走通的续跑路径**：本例修完时序才发现续跑函数的准入条件写的是老计费模式的列（要求 `已扣费 + 已退款`），而按次计费运行永远是 `reserved / 未退款`——**续跑机制对每一个按次计费运行都是不可达的**，窗口开了也没处可去。同一个根因的第二张面孔：**按计费模式分别给出「钱这边可以复用」的证明**，别用一种模式的列去判另一种模式的运行。
- **预防**：**任何在失败路径上执行的不可逆外部副作用，都会把「可重试的失败」变成「不可挽回的失败」**。审计每一条 `catch` / 失败分支里的外部调用，问一句：这个动作如果在 bug 修好之后被证明是多余的，还能撤回吗？撤不回就不该放在这里。另注意结清之后通常**只能补扣不能重开**（补扣走另一个确定性 operation），所以别指望「改回 reserved 再结一次」——那是对外部账务系统的猜测。

### 「用户点一下就扣一次费」的入口没有总量上限

- **现象**：桌宠 `老鼠猫` 运行里，同一个动作 `row-running-right` 独吞了 10 次付费重试，整条运行 23 次真实调用（4600 积分）最后一张图都没交付。用户面对的是一个「差一点就好了」的动作，点「批准重试」点了 10 次。
- **根因**：批准接口每次只把该任务自己的 `maxAttempts` 加一，**没有任何总量口径**——既没有单任务上限，也没有运行级上限。上游又恰好有一条过严的像素判定（合取门禁，一格瑕疵废整块付费板）在持续制造「差一点」的错觉，两者叠起来就是一个可以无限点的扣费按钮。
- **修法**：加两级上限（单任务 4 次 / 单次运行 12 次，可用环境变量覆盖），**在扣费之前**判，超限返回 409 并把当前用量回给前端。阈值不是拍的：翻历史流水，单任务真实需要的付费重试最多 2 次，病态那次是 9 次。超限的出路是「失败续跑 / 复制为新工作」，而不是继续在同一个动作上烧钱。
- **上限要从计费流水点，不要从 `attempt` 计数器点**：`attempt` 也会因为 provider 传输失败而前进，而传输失败是要退款的。用 `attempt` 当预算，等于让上游抖动消耗用户的付费修复次数（本例有过连续 6 次 socket 失败，会直接吃掉 1.5 个任务的预算）。计数只认「钱已经花出去」的状态（在途 / 已发 / 已成功），退款过的失败不计。在途状态必须计数，否则双击批准能绕过上限。
- **预防**：**任何「用户点一下就真实扣一次费」的入口都必须有总量上限，且上限判定要在扣费之前**。设计重试授权时，一并回答「第 N 次之后怎么办」——没有出口的重试循环，最后一定是用户在替一个 bug 反复付费。

### 「请求发出去过」被当成「用户拿到了东西」来计费

- **现象**：一个**已完成**的桌宠运行结清了 12 单位，其中 9 单位是 `status=failed` 的调用——**为 9 张没生成出来的图收了 1800 积分**。另有失败的计划外调用，扣费时独立扣了 200 积分，之后没有任何退款路径。
- **根因**：结清单位数按「已发出请求」点（`sentAt != null`），没排除 `status: "failed"`。计划外调用更直接：批准时就先扣费，provider 之后失败与那笔扣费在代码里毫无关联——运行级的退款字段对这种按次计费模式永远是「无退款」。
- **修法**：调用流水表加 `refundStatus` / `refundedAt` / `refundError` 三列，失败落库后按**这次调用自己的 `operationId`** 退款并发事件；结清口径统一加「排除失败」。退款做成 **best-effort**：回执写在流水行上，计费服务抖动时留 `pending` + 错误原文供重试，不要让退款失败反过来把整条运行搞失败。
- **同一条口径在仓库里出现几次，就要一次全改到位**：本例「结清单位怎么点」写在三处（runner 结清、worker 定时清算、取消退款）。第一版只改了 runner，取消路径会继续安静地按老规则对失败调用收费。改计费口径前先全仓搜一遍这个 where 条件。
- **注意区分两种「数失败调用」的语义**：结清单位数**要排除**失败调用；而「这次失败到底有没有动过钱、有没有可续跑之物」那种判断**必须包含**失败调用——否则会把有素材可救的失败误判成零成本失败而立即结清，触发上一条「结清即终态」的死刑。同一张表、同一个 `count`，语义完全相反，注释要写清各自回答什么问题。
- **预防**：**计费口径要挂在交付结果上，不是挂在「发出了请求」这个动作上**（同源问题见本节「按请求参数计费，上游却缩水交付」）。凡是「先扣费、后异步执行」的设计，扣费那一刻就要同时想清楚失败时谁负责退——退款路径不是补丁，是这个设计的必要组成部分。

### 「等人操作」的状态没有超时：占住额度的僵尸 + 醒来抢配额

- **现象**（桌宠只读复查发现，**已修**）：按次计费运行每次失败都停到 `awaiting_regeneration_approval` 等人点批准。这个状态**被 stale-run 回收显式排除**（人还没点，不该抢走），**也不在定时结清的候选集里**（只扫 `ready`/`cancelled`/超期 `failed`），于是它的整笔预留（14 单位 / 2800 积分）被**无限期**占住。更要紧的是它**不在「已有活跃运行」的拦截名单里**，用户可以另开新运行；某天回头把老的批准了，**两条运行同时打同一份上游配额** —— 正是当初把这条链路打死的那种 429。
- **根因**：「等待人工」被当成一个中性的暂停态处理，但它同时是**账务上的未决态**和**执行上的可唤醒态**。三处口径各自只看了自己关心的那一面：回收看「有没有 worker 在跑」，结清看「是不是终态」，新建拦截看「是不是活跃」——三个都判它「不用管」。
- **修法**：新增 `BLOCKING_RUN_STATUSES = [...ACTIVE_RUN_STATUSES, "awaiting_regeneration_approval"]`，判据换成「这个账号有没有一条**可能打到上游**的运行」——停摆运行虽然没在跑，一批准就立刻派发付费调用，所以必须算进去；新建/续跑/恢复三个入口统一走它，报错文案点名出路。另加 `expireParkedCodexPetRuns` 兜底回收：超期的无主停摆运行转 `cancelled`、结清预留、退掉已扣费未派发的额外调用，事件带 `reason: "approval_expired"`。扫描与用户点批准之间的竞态靠 `updateMany` 命中 0 行自然让位。详见 [codex-pet.md 6.12.7](codex-pet.md)。
- **预防**：**任何「等人操作」的状态都要有过期时间**。没有超时的等待态会同时留下两笔债：占住的额度，和一个随时可能被唤醒去和现役任务抢配额的僵尸。检查清单：这个状态会被 stale 回收吗？会被结清吗？会挡住新建吗？三问里有「不会」，就要能说清为什么不会出问题。

### 扣费挂在「动作」上、退款挂在「结果」上，中间的状态差就是漏钱窗口

- **现象**（桌宠只读复查发现，**已修**）：批准重试时**先扣费**再把任务置入队列。若在 worker 领活之前用户取消运行，这条流水停在 `prepared`：**不是 `failed`**，而退款函数的准入条件恰恰是 `status === "failed"`；取消路径的按次计费分支又只结清计划内预留、从不退已扣费的计划外调用 —— 200 积分留在系统里，没有任何一条路会退。
- **根因**：扣费点选的是「用户批准」这个**动作**，退款条件写的是「provider 失败」这个**结果**。两者之间隔着「已扣费、还没执行」的中间态，而这个中间态在退款条件里没有对应项。
- **修法**：`refundCodexPetUndispatchedExtraCalls` 按运行清扫停在 `prepared` 的计划外调用（`sent`/`succeeded`/`failed` 各有自己的归宿，计划内一律不碰），幂等，退款接口抖动留 `pending` 给重试；取消与超期回收两条路径都会调它。详见 [codex-pet.md 6.12.8](codex-pet.md)。
- **预防**：**扣费点和退款条件必须按同一个维度描述状态**。设计「先扣费、后异步执行」时，把两者之间**所有**中间状态列出来，逐个回答「停在这里时钱怎么办」——列不出来的那个状态就是漏钱窗口。相邻路径别一起改：扣费本身失败（置 `cancelled`）和入队失败（stale 回收自愈）这两条通常是好的。

### 多副本重复消费任务

- **现象**：API/Worker 多副本时，同一任务可能被并发认领。
- **根因**：缺少事务性认领。
- **修法**：Postgres 租约模式，`SELECT ... FOR UPDATE SKIP LOCKED` 在事务里锁行认领 + 心跳续租 + 过期回收（`codex-pet-runner.ts`）。
- **预防**：新异步业务线优先复用租约模式，而非再引入新队列中间件。

## 四、本地开发环境

### macOS 下 `Ctrl+C` 后进程杀不干净

- **现象**：停止开发服务后，pnpm/tsx/Vite/esbuild 的孙进程残留，或进程卡在 E（exiting）状态忽略 TERM。
- **根因**：子进程被重新 parent 到 launchd；macOS 进程可能卡在 E/Z 状态。
- **修法**：`scripts/dev-local.sh` 用 `set -m` 给每个服务独立进程组，退出时按 PGID 发 TERM、宽限 10 秒再 KILL；每秒巡检，连续 5 次观察到 E/Z 状态就整体退出。
- **预防**：改开发编排脚本时保留进程组与僵死检测逻辑。详见 [overview.md](./overview.md)。

### zsh 下 `. .env` 直接报错，导致「以为 source 了其实没有」

- **现象**：按 `docs/ai-collaboration.md §1.1` 执行 `set -a && . .env && set +a`，zsh 报 `(eval):.:1: no such file or directory: .env`，尽管 `.env` 确实存在于 cwd。
- **根因**：zsh 的 `.` 内建只搜 `PATH`，不像 bash 那样回退到当前目录。`PATH` 里没有 `.`，于是找不到。
- **修法**：写成 `set -a && . ./.env && set +a`（显式 `./` 前缀）。
- **预防**：**这条比它看起来严重。** source 失败后若不检查退出码就接着跑测试，得到的正是 12 个 `describe.skipIf` 文件静默跳过、退出码 0 的假绿。source 后先 `echo "${DATABASE_URL:+set}"` 确认一句，再跑测试。

### turbo `passThroughEnv` 使缓存命中重放「无 env」的旧测试结果

- **现象**：`pnpm test` 显示某 workspace 绿，但那次运行实际是 `cache hit, replaying logs` —— 数字可能来自某次没 source `.env` 的运行，此刻是否真的绿并未验证。2026-08-03 实测一次 `pnpm test` 中 **7/10 个 workspace 是缓存命中**。
- **根因**：`turbo.json` 的 `test` 任务把 `DATABASE_URL` / `BILLING_BASE_URL` / `S3_*` 等 ~49 个变量列在 `passThroughEnv`。该字段**只负责透传给子进程，不参与缓存哈希** —— 有 env 与无 env 两次运行的 cache key 完全相同，后者的结果会被前者复用（反之亦然）。
- **修法**：需要可信数字时用 `turbo run test --force`（可配 `--filter` 只重跑缓存命中的那些）。核对 `Cached: 0 cached` 再采信。
- **预防**：CI 里给 `test` 任务设 `cache: false`，或把 DB/Redis 类变量从 `passThroughEnv` 移到 `env`（参与哈希）。否则「skip 计数不得超过基线」这类假绿防护本身会被缓存重放绕过 —— 防护和被防护对象踩同一个坑。

### grep 扫到单行超大 JSON 刷爆输出

- **现象**：全仓搜索时输出被 `apps/api/src/tool-market/data/*.json` 的单行超大内容刷爆（曾多次中断会话）。
- **根因**：tool-market 的技能站点目录是单行巨型 JSON，`grep` 命中后整行打印。
- **修法**：搜索时排除 `tool-market/data`（`--exclude-dir=data` 或限定文件类型）。
- **预防**：全仓搜索默认排除数据目录与 `node_modules`。

## 五、部署与回滚

### 回滚旧镜像不会自动删除新增 Deployment

- **现象**：回滚到不含 Codex 桌宠的旧 API 镜像后，`codex-pet-worker` 仍在运行。
- **根因**：`kubectl apply` 不会删除清单里新增过、回滚清单里没有的 Deployment。
- **修法**：回滚前先隐藏 `workflow.codex-pet` 菜单、停止新运行、等待或取消存量运行，并手动 scale/delete `deployment/codex-pet-worker`。
- **预防**：新增独立 Deployment 的特性，回滚步骤要显式包含删除该 Deployment。详见 [overview.md](./overview.md)。

### 发版用一次裸 `kubectl apply -k` 绕过迁移门禁

- **现象**：直接整体 apply 可能在迁移未完成时就滚动了应用。
- **根因**：迁移与滚动没有顺序约束。
- **修法**：`scripts/release.sh` 契约——先构建推送同版本镜像 → 删除固定名 `migrate` Job → 单独应用迁移并等待 Complete → 才滚动 API/Worker/前端。
- **预防**：迁移是发版硬门禁，不能用裸 apply 代替。

### 桌宠交付链路要求 HTTPS 公网地址

- **现象**：本地 HTTP 环境下无法真正验证 Codex 安装深链。
- **根因**：签名产物下载与 Codex 导入需要外网可达的 HTTPS `CODEX_PET_PUBLIC_BASE_URL`；本地 HTTP 只能验证工作流与签名路由本身。
- **修法**：本地开发允许 HTTP（`dev-local.sh` 有注释说明），生产 `codex-pet-routes` 强制要求显式 HTTPS 的 `CODEX_PET_PUBLIC_BASE_URL`。
- **预防**：涉及外部平台导入的交付物，尽早在真实 HTTPS 环境跑 POC。详见 [codex-pet.md](./codex-pet.md)。

## 五点五、富文本与生成产物

### 富文本编辑器静默拍平生成结果，自动保存把它写回库

- **现象**：公众号图文生成完好，点进编辑态**什么都没改**，刷新后正文成了一串空段落，配图重复堆在末尾。库里两行被毁：一行可见文字归零、`bodyHtml` 从正常尺寸涨到 11.4 MB（4 张图的 base64 被反复追加），另一行三层 `section` 拍平成单个 `<p>` 只剩 269 字。
- **根因**：三个独立机制叠在一起，单看每个都"正常"：
  1. wangEditor（底层 Slate）是 **schema 型**编辑器，`section` 不在它的模型里，**载入时**就被剥成 `<p><br></p>`——不是用户操作导致的，是 `setHtml` 自己干的。
  2. 编辑器把这次载入改写当成内容变更抛了 `onChange`，而脏标记是**无条件**置位的（`markDirty(platform, true)`），1.5 秒自动保存照常发车。
  3. 拍平把 `data-ai-assistant-image-slot` 一起弄没了，而 `replaceWithImageSection` 找不到槽位时**回退到 `root.appendChild`**——于是每存一次就把每张图再追加一份。三者串起来：打开即毁，且毁得越来越大。
- **修法**：按「先止血、再拔根」的顺序，四层各修一处：
  1. **服务端兜底**（`article-workflow-html-guard.ts` 的 `assertArticleWorkflowBodyNotDestroyed`）：PATCH 时拿新正文跟**库里旧正文**比，「原来有文字现在归零」和「原来有图片槽位现在一个不剩」两种整体销毁形态直接 422 拒绝。判定是相对的，所以本来没图的文章、以及修复已损坏行的写入都不会被锁死。
  2. **自动保存改成内容驱动**（`useArticleWorkflowStudio.ts` 的 `syncDirtyByContent`）：脏标记由完整草稿哈希与 `lastSavedHashRef` 比对得出，不再由「有没有收到 onChange」决定。失焦提交也过同一道比对——编辑器一打开就会失焦一次，那一发绝不能写库。
  3. **换掉编辑器**：改用 DOM 型的 Squire，见 [ADR-010](decisions.md)。
  4. **词汇表同源**（`packages/article-workflow/src/html-vocabulary.ts`）：服务端 guard 与前端 sanitizer 读同一份标签/属性白名单。原始 bug 的本质就是"编辑器认的"和"服务端认的"两份规则各写各的。
- **预防**：
  - 拿富文本编辑器承载**机器生成的 HTML** 前，先做一次零编辑回环：`setHTML(原文)` → 立刻 `getHTML()` → 逐项比对标签数、嵌套层级、内联样式、业务用的 `data-*`。这一步在选型阶段一分钟就能做，比上线后翻库补数据便宜得多。锁死用例见 `ArticleWorkflowRichEditor.roundtrip.test.tsx` / `.normalize.test.tsx`。
  - 「脏」的定义永远用**内容比对**，不要用「收到过变更事件」。第三方组件的变更事件里混着它自己的规范化。
  - 用 `data-*` 当锚点的回写逻辑，找不到锚点时**必须失败或跳过，不能 append 兜底**——静默兜底把"少一张图"放大成了"库涨到 11 MB"。
  - 排查这类问题时，**别把损坏字段原文打到终端**。这行 11.4 MB 正文里的残留标记混进过工具输出。一律用去标签、限长度的脚本只看结构（标签序列、计数、槽位名）。

### 配图 base64 写进正文，一篇稿子 10 MB、详情接口 31 MB

- **现象**：图文生成显示成功，页面能打开但明显发卡。实测某一行 `bodyHtml` **10,548,130 字节**，详情接口返回 **31,641,351 字节 / 0.602 s**。7 行历史数据合计 197 MB。
- **根因**：`storeWorkflowImage` 有个本地开发便利分支 `shouldInlineStoredImageForLocalEndpoint`——没配 `IMAGE_S3_PUBLIC_BASE_URL` / `S3_PUBLIC_BASE_URL` 且 S3 端点主机名是 localhost/127.0.0.1/::1 时，**即使字节已经上传成功**也返回 base64 data URL。图文工作流拿这个返回值当图片地址用，于是同一张 2 MB 的图被存了三份：正文的 `<img src>`、manifest 的 `imageUrl`、manifest 的 `thumbnailUrl`。图片数 × 3 × 单图大小，线性放大。
- **修法**：地址分成「落库形态」和「出参形态」两套，见 [ADR-011](decisions.md)。落库存 `/api/workflow/article-workflow/images/<assetId>/blob`，出参时现签短期签名，保存前把签名摘回去。同一条 URL 上线后：详情接口 31.6 MB → **8,583 字节**，0.602 s → **0.0087 s**。历史数据用一次性脚本按 manifest 重建正文修复（字节本来就在对象存储里，**不重新生成、不计费**），6 行修复、释放 177.8 MB。
- **预防**：
  - **别让「本地开发便利分支」的返回值流入会落库的字段**。这个 inline 分支本身没错（本地不配对象存储也能看到图），错在图文链路把它的返回值当成了可以长期存的地址。判断标准很简单：这个值会不会被写进数据库？会，就不能接受 data URL。
  - 换地址前先确认**字节确实在别处存着**（`objectKey` 非空）。没配对象存储时 data URL 是图片的唯一副本，无脑替换等于删图。这一条在实现里是硬条件：`assetId && objectKey` 同时成立才换。
  - 加了「出参每次都不一样」的字段后，**顺手检查前端的脏判定/差异比对**。本例里签名的 `exp` 每次都变，不在哈希里摘掉就会让每一行永远处于「未保存」状态、自动保存每 1.5 秒发一次。
  - 体积类问题**用测量说话**：同一个接口改前改后各打一次字节数和耗时，比「感觉快了」有用。回归用例直接钉字节上限（`expect(row.bodyHtml.length).toBeLessThan(4096)`）。

### 排版模型换了个标题层级，整篇生成判失败

- **现象**：页面报「微信公众号生成失败：HTML 包含未允许的标签: `<h2>`」，重试时而成功时而失败。
- **根因**：白名单只放行了模型**上次**用的那几个标签。模型在等价表达之间自由摆动（这次 `h2`、下次 `h3`），而校验是「不合规就整篇抛错」，于是失败率取决于模型今天的心情。
- **修法**：白名单按**语义等价类**放开（`h2`/`h3`/`h4` 一起放行，见 `packages/article-workflow/src/html-vocabulary.ts`），并在抛错前加一层 `repairArticleWorkflowHtmlFragment` 尽量修，修不动才失败。
- **预防**：校验模型输出时区分两件事——「**语义上不能接受**」（`script`、`iframe`、定位类样式）该硬拒；「**风格上不一样但等价**」（标题层级、`strong` 与 `b`）该收进白名单或修掉。把后者也做成硬拒，等于把生成成功率押在模型的用词习惯上。改白名单时记得连带更新断言反向的用例：本次就有一条「`h2` 应被脱壳」的旧用例在 `h2` 放行后才暴露出来。

## 六、业务逻辑（来自深度报告）

以下为高频教训摘要，完整取证与修复过程见对应报告：

- **评分算法饱和导致趋势图失真**：小说 31 章张力全部为 100，概览图只画张力不画质量，看起来"每章都一样"。根因是评分算法严重饱和 + 展示缺项，不是数据没变。详见 [novel.md 附录 A](novel.md)。
- **只有"新增检测"没有"生命周期状态机"**：伏笔与叙事债 31 章无变化，因为系统只检测新增、不做强化/回收/关闭的状态流转，还叠加了历史脏数据。教训：跨章演进的实体必须建真正的状态机。同上报告。
- **可观测性要提前留档**：生成请求当时只存了参数与结构化上下文快照，没存最终发给模型的完整 system/user prompt，事后无法精确复现。教训：付费/复杂生成链路要留 prompt 审计。同上报告。
- **计费只数作者可见文本**：小说计费口径是只统计作者可见值、不数 JSON key（`workflow/novel-billable.ts`），避免结构化输出把计费撑大。
- **`kind.includes()` 归类 + 取最新，会稳定挑出错的那个（已修）**：桌宠「当前桌宠姿势板」实际显示的是方向盲测图。筛选口径 `kind.includes("direction")` 误捞了方向质检图，而质检图产在流水线末尾的校验阶段、永远比姿势板新，取 `[0]` 就永远是它。故障表现是「显示了错的图」而非空白，比空白难发现得多。详见 [codex-pet.md 6.9](codex-pet.md)。
- **带 TTL 的中间产物不要占交付位（已修）**：姿势板有 7 天 `INTERMEDIATE_TTL_MS`，放在面向用户的工作台上只能在「显示错图」和「显示空白」之间二选一 —— 上一条那个过宽筛选就是为了「总能填上点什么」才写成 `includes`。修法是把姿势板/方向质检图整体下沉到工作台底部默认折叠的「过程产物（内部诊断）」，在那里过期即为空是预期行为。产物本身必须留（provider 计费指标、定向续跑锁定已付费失败板、已出图恢复重切帧都依赖它），只是不该展示在交付区。详见 [codex-pet.md 6.9.1](codex-pet.md)。
- **同一个 kind 覆盖的范围可能超出界面语义（已修）**：桌宠「状态动画预览」那格取最新的 `animation_preview`，但这个 kind 除九个标准行外还包含 `look-a` / `look-b` 两个方向行，且方向行产得更晚 —— 全库 324 个运行里 294 个（91%）显示的是一个无标注方向动画，剩下的与下方九格重复。修法不是收紧取值，而是把已有的「9 组标准动画」九宫格从交付面板挪到运行期就渲染（每格按 jobKey 精确匹配、缺的显示占位、标题带「已完成 N/9」），再删掉这一格。**排查提示**：改前先按 `metadata->>'jobKey'` 分组数一遍，别假设一个 kind 只对应界面上那一类东西。详见 [codex-pet.md 6.9.2](codex-pet.md)。
- **恢复类运行必须把用户可见产物落到新 runId 下**：桌宠工作台按 `latestRun.id` 隔离所有可视产物（防止失败运行的候选图看起来可交付），而人工恢复运行只重建 spritesheet/preview/package，于是九格标准动画全空 —— 图其实都在，只是挂在上游失败运行下。另外 `objectKey` 嵌了 runId 且服务端校验前缀一致，补数据不能只 `UPDATE runId`，必须重新上传。详见 [codex-pet.md 6.8](codex-pet.md)。
- **降级成 warning 但不擦除像素，等于把状态泄漏给下游（已修）**：桌宠邻格渗漏判定命中后只把 finding 从 error 降成 warning，像素留在原地 —— 于是它撑宽了裁剪框、活进归一化图集格，而在图集格里**不再贴边**、渗漏特征消失，于是在第二层校验里以硬错误身份复活，废掉整张已全部付费的图集。**降级只改变「这次要不要报错」，不改变「这堆像素还在不在」**；下一层用不同坐标系和特征重看同一堆像素，结论可以完全反转。多层校验流水线里「降级」与「擦除」必须显式二选一，擦除则必须留痕（本次补了 `removedBleedComponentCount` 并照报 warning，因为悄悄丢像素正是让这条链路难排查的那个失败模式本身）。配套教训：**测试要盯不变量，不要只盯严重级别** —— 只断言「降级成 warning」会让这个 bug 继续躲过测试，得断言裁剪框、连通域数、下一层校验结果。详见 [codex-pet.md 6.11.2](codex-pet.md)。
- **校验失败时把「已经算出来的合格部分」一起扔了（已修）**：桌宠抽帧器无论成败都会把全部帧和逐帧诊断算完返回，但 runner 的失败分支只落原始板图和一份**不含帧**的报告，写帧产物的代码只在成功分支里 —— 于是一格坏帧会让**同一次付费调用里 7 格合格帧**连同它一起消失，下一次批准是整块重画。反证很硬：事后的人工救援脚本零生图、纯靠**已存帧**就拼出了合格产物，说明「好帧可复用」不是设想，只是产品里没有这条路。**判定层返回了逐项诊断，就说明作者本来打算让调用方按项处置；调用方只取一个 `ok` 布尔值，等于把这份信息量白白丢掉**。付费产物的失败分支，落盘信息量应当**不少于**成功分支 —— 成功时只需要结果，失败时才最需要中间态。**修法**：失败分支把逐格健康度记成 `metadata.salvage`（schema 带版本号），下一次重画先取同一 `jobKey`、同一 `inputRevision`、同几何的最近一条捐赠板，只把**新板失败、老板合格**的槽位拼回来，且只在覆盖率**严格变好**时才接受。拼接必须发生在**原始源板槽位**上、不能拿已抽好的帧去拼——抽帧器对整块板只算一份共享缩放和一条基线，混合来源的帧会各自带着别人的基线。详见 [codex-pet.md 6.12.1](codex-pet.md)。
- **整体校验放在所有付费步骤之后、且没有局部补救路径（已修）**：桌宠有四道硬性图集闸门（拼装结构检查、图集校验、方向连续性、打包再校验一次）全部位于 14 次付费调用**之后**，任一失败就是整条运行判死刑；唯一存在的有界修复循环只对**质检结论**做反应，对这四处结构性 `throw` 一概不接。用户视角就是「九组动画都出来了，为什么还是失败」。附带的坑：其中两道跑在「关闭质检」这个开关**之前**，**关了质检也挡不住**，且看不出为什么。**整体校验的失败信息必须能反向映射到某一个可单独重做的单元**，否则它只能表达「全部重来」；而放在所有付费动作之后的「全部重来」，就是把整条流水线的成败押在最后一次拼装上。**修法**：让图集校验**逐单元格**归因（错误前缀带 `状态[列]:`，色键残留按所在格计数并且总数与逐格之和恒等），再把这些格反向映射回**唯一那个可以单独重做的单元**——产出它的那次板调用；闸门失败时把归因结果连同 schema 版本落成快照，只重置被点名的那几行，其余 22 个 job 的已付费产物原样保留。归因表只有一份单一真源（`CODEX_PET_GATE_REPAIR_ROWS`），免得「哪些行可修」在三处各写一遍。详见 [codex-pet.md 6.12.2](codex-pet.md)。
- **报错文案给出的出路，在当时那个状态下点不到（已修）**：桌宠重试超限返回 409，文案说「请改用失败续跑或复制为新工作」——但触顶时运行停在等待批准态：「复制为新项目」按钮的显示条件是**终态**（不出现），「失败续跑」要求状态是 `failed`（不可用）。实际唯一通路是**先取消运行**、变成终态之后再复制，而文案一个字都没提。同源的第二处：那条「失败续跑」的准入条件是「存在 prompt 版本落后的任务」，而图集闸门失败时所有任务都已完成且都是当前版本 ⇒ **对这种失败形态根本不可达**，上游好不容易开出来的可续跑宽限窗口没有任何消费者。**写文案时按的是「概念上存在这条路」，用户按的是「这个按钮现在在不在」**；续跑准入也不要用「代码版本变了没」当唯一代理指标，它只覆盖「因为老 prompt 失败」。**修法**：409 文案改成写当时真的点得到的那一步，并把结构化用量一起带上；续跑准入不再只认「prompt 版本落后」，闸门失败落下的那份快照本身就是准入凭据，一次性消费（读过即失效，不会让一份快照被反复兑换成免费重跑）。详见 [codex-pet.md 6.12.3 / 6.12.4](codex-pet.md)。
- **零重试 + 每次重试都要人点：不漏钱了，但会「点很多次还不成功」（已修）**：桌宠按次计费下把传输层重试次数钉成 1，一次 socket 抖动就把运行停到等待批准。钱这边是干净的（失败会退款、且不消耗重试预算），但体感是运行在「抖动 → 停摆 → 用户批准 → 抖动」之间无限来回。**「每次调用都要用户点一下」的设计，必须先把不需要用户判断的失败挡在用户面前之外** —— 区分「传输层失败」（在已扣费额度内自动重试）与「质量不合格」（才停下来问人），否则用户是在替系统做重试。**修法**：把两件事拆成两根独立的轴。**传输轴**——同一次已付费调用因网络抖动而重发，回到**同一条流水行**、不产生新的计费单位、也不消耗额外调用预算，因此可以自动重试，用户不该看见；**质量轴**——板子画得不合格要重画，每次重画都是一个新的计费单位、必须单独授权，所以在按次计费下钉成 1。**这里有一条留在设计里的取舍**：计划内 14 次调用零余量，质量不过关的重画依然逐次计费、逐次授权，这是明确的设计而不是漏洞。详见 [codex-pet.md 6.12.5](codex-pet.md)。
- **后端特意回给前端的结构化错误数据，在 API 封装层被丢掉（已修）**：桌宠重试超限的 409 特意带了 `data.extraCallBudget`（用量/上限），但前端统一请求函数只取 message + status 抛异常，**结构化字段在这里蒸发**，于是批准面板始终不显示「本动作已用 3/4」，用户只能撞到 409 才知道到顶。加结构化错误字段时**顺着调用链验到渲染那一层**为止 —— 只到「后端返回了」不算做完。**修法**：`ApiError` 带上 `data`，读错误体的地方保留整个 body，批准面板直接显示本动作/本运行的额外调用余量。同一批还揪出一个同源问题：界面上那个「预留 = 单价 × 14」是写死的，后端改计划次数它不会跟着动，改成从定价接口的 `plannedImageCallLimit`（外加运行行上冻结的那份）派生，前端常量只做加载前兜底。详见 [codex-pet.md 6.12.10](codex-pet.md)。
- **改了计费政策，注释还留在旧世界（已修）**：桌宠调用流水里仍写着「fetch 之后的 socket 错误照旧计费，因为请求可能已经到达上游」，而政策早已改成**不看是否已发出**一律退款/一律排除在结清之外（平台吸收已打到上游的成本）。方向对用户有利，但**照着这条注释改代码会把漏钱补回去**。改计费口径时，把解释旧口径的注释当成需要一起改的代码。详见 [codex-pet.md 6.12.9](codex-pet.md)。
- **并发默认值挑的是「跑得快」，代价是自己给自己造 429（已修）**：桌宠视觉并发默认 3，两个 base 候选于是**默认就并发两次真实生图**——去抢的是同一份上游 relay 配额，等于自己把自己打成 429，而这正是当初把一条真跑打死的那个错误。反差很明显：同一份代码里 9 个标准行是**严格串行**的，注释还写明「避免五个互不相关的付费调用同时在途」，说明作者在别处已经想清楚了，只是这个默认值没跟上。**一个并发默认值，要按它的调用点在派发什么来定**：派发的是幂等只读请求，并发是优化；派发的是**受配额约束的付费调用**，并发就是风险，默认必须串行、想并发的人显式开。改默认值时顺带撞出一条测试回归也值得记：那条「取消兄弟任务」的契约只有在并发 > 1 时才存在，串行下兄弟根本没起过——**这种测试要显式 pin 出它依赖的配置，别靠默认值供着**，否则它会在某次调默认值时无声变成一条什么都没验的测试。详见 [codex-pet.md 6.12.11](codex-pet.md)。
- **零容忍合取门禁会让一处瑕疵废掉整批付费成果（已修）**：桌宠一次付费调用在一张 `4×2` 板上出 8 个姿势，而 `ok: errors.length === 0` 让任意一格触发任意一条硬像素规则就整板作废、重试再扣费 —— 同一个动作因此重试了 11 次。更根本的是那几条规则惩罚的是**排版方式本身**：槽位边界是对源板做的纯算术等分、没有印刷装订线，相邻姿势天然在共享边界留浅边。**判定阈值要对着「产物实际是怎么排版的」定，不是对着理想像素定**；任何 `errors.length === 0` 式门禁都要先问：一条失败该废掉多大范围的付费成果。放宽时保留一个 `strict` 模式逐字复现旧行为并在测试里双向断言，才能证明放宽是有意的而非把判定改坏。详见 [codex-pet.md 6.11.1](codex-pet.md)。
